互动计数异步化设计与实现

日期：2026-11-15。源码基线：`backup-before-reset-20261107`，`30d3a6b`。下文保留设计与验收标准；实现状态及实际验证记录见文末，示例峰值不是实测性能。

1. **成功边界与优化目标。**

   点赞、收藏关系和评论正文仍同步提交 MySQL。接口成功表示业务事实与待发送事件已经提交；总计数由后台更新。前端在原有数字上乐观加减，不等待全局精确总数。

   请求事务不再对视频执行 `SELECT ... FOR UPDATE`，也不再更新 `videos` 中的三类互动计数。点赞、收藏、评论不再通过这条视频记录主动争抢排他锁。关系唯一索引、具体关系行、Outbox、数据库资源仍然有自己的并发成本。

   MQ 将瞬时积压留在队列中，后台以有限并发处理。后台写计数时仍有行锁；一个计数 Worker 加批量合并可以减少并发争用和计数更新次数。持续输入超过处理能力时仍会积压，不能把 MQ 当成无限吞吐。

2. **当前实现里必须一起处理的地方。**

   - `backend/internal/video/like_repo.go`、`favorite_repo.go`、`comment_repo.go`：事务先锁视频，修改事实、计数和通知 Outbox。
   - 现有通知事件只覆盖部分新增互动；给自己点赞/收藏/评论没有通知，取消互动也没有相应通知。计数事件必须独立生成，否则会漏算。
   - `notification/outbox_publisher.go` 把所有事件路由写死为 `notification.<EventType>`，需要为计数事件增加显式路由。
   - `mq.Client` 的队列和 Prefetch 来自单份 Config；计数队列需要独立队列声明、消费参数和 Channel。
   - 前端 `useLikeFollow.ts`、`VideoDetailView.vue` 直接采用响应里的总数，需要同步修改 API 类型及页面逻辑。
   - 现有视频模型和互动模型没有声明视频外键关联；实际数据库约束需要用 `SHOW CREATE TABLE` 核实。不能假定已经有外键保护删除并发。
   - `view_repo.go` 仍同步更新 `videos.view_count`，这是一条已确认的剩余视频行写热点。本轮针对三类互动计数，不能宣称全部视频写路径已无热点。

3. **完整调用链。**

   ```mermaid
   flowchart TD
       A[用户点击点赞] --> B[前端保存旧状态并本地加一]
       B --> C[接口写点赞关系和 Outbox]
       C --> D{MySQL 事务提交}
       D -->|成功| E[返回 is_liked 和 changed]
       D -->|确定失败| F[前端恢复旧状态]
       D -->|成功| G[后台认领 Outbox]
       G --> H[发布到 feed.events 并等待 Broker 确认]
       H --> I[feed.counter 队列]
       H --> J[feed.notification 队列]
       I --> K[计数 Worker 去重并合并增量]
       K --> L[事务更新 video_counters 和消费记录]
       L --> M[提交后 ACK]
       J --> N[现有通知消费者]
   ```

   计数与通知使用各自的 Outbox 记录、路由和队列，图中的两条支路不表示同一条消息自动承担两种职责。自己给自己点赞仍产生计数事件，但不产生通知事件。HTTP 请求不等待 Outbox 发布或消费者处理。

4. **新增两张表，复用现有 Outbox。**

   | 表 | 关键字段 | 责任 |
   | --- | --- | --- |
   | `video_counters` | `video_id` 主键；`likes_count`、`favorites_count`、`comments_count`；`updated_at` | 展示计数投影 |
   | `video_counter_consumptions` | `event_id` 主键；`processed_at` | 标记已应用的计数事件 |
   | 现有 `notification_outbox` | 复用 `EventKey`、`EventType`、`Payload`、认领令牌、租约、发布时间 | 同事务持久化待发送事件 |

   第一版沿用 Outbox 的现有包名和表名，避免为了命名扩大重构。`video_counters` 的三个计数使用有符号 `BIGINT`；`video_id` 类型必须与实际 `videos.id` 完全匹配。消费记录不级联依赖视频，避免删视频同时删掉重投去重依据。

   新视频与零值计数行在同一个事务中创建。旧数据在切换前从事实表回填。旧 `videos` 计数字段暂留作兼容迁移，但切换后不再作为这三个计数的读写来源。

5. **生产端只为真实变化产生事件。**

   | 业务动作 | 事实写入 | 实际变化后的计数增量 | 通知 |
   | --- | --- | --- | --- |
   | 点赞 | 插入 `likes` | `like +1` | 对其他作者按原规则发送 |
   | 取消点赞 | 删除当前用户的关系 | `like -1` | 无 |
   | 收藏 | 插入 `favorites` | `favorite +1` | 对其他作者按原规则发送 |
   | 取消收藏 | 删除当前用户的关系 | `favorite -1` | 无 |
   | 评论 | 插入正文 | `comment +1` | 对其他作者按原规则发送 |
   | 删除评论 | 校验作者后删除指定评论 | `comment -1` | 无 |

   点赞以普通 INSERT 配合现有 `(video_id, account_id)` 唯一约束处理：确实插入才写 `+1` 事件；只将对应唯一键的重复错误作为幂等成功，其他数据库错误返回失败。收藏相同。避免用“先普通 SELECT 判断不存在，再无条件 INSERT”承担并发正确性。

   取消点赞/收藏使用带完整关系条件的 DELETE，以 `RowsAffected` 判断是否真实删除。只有删除一条才写 `-1` 事件；重复取消不生成事件。计数事件使用独立事件 ID，不需要为取得旧关系 ID 而锁视频或先查关系。

   评论删除只有实际删除成功才产生扣减事件。消息幂等不等于评论 HTTP 请求幂等：第一版保留当前正文提交语义，前端防止重复点击；不将超时重发评论宣称为自动去重。

   ```text
   开始事务
     读取视频必要信息（普通查询，用于存在性和作者信息）
     修改当前用户的关系，或评论正文
     如果确实发生变化：
       写计数 Outbox
       如符合通知规则，再写现有通知 Outbox
   提交事务
   返回确认的互动状态，不查询最新全局计数
   ```

   即使操作人为作者本人，也必须生成计数事件。通知 Outbox 写入或计数 Outbox 写入失败时，事务整体回滚。

6. **计数消息传增量，不传前端总数。**

   Outbox `EventType` 固定为 `counter.video.delta`，`EventKey` 与消息 `event_id` 一致。事件 ID 在写 Outbox 时生成并持久化，可采用 `counter:` 加 128 位随机 ID；再次发布同一 Outbox 时使用同一 ID。

   ```json
   {
     "version": 1,
     "event_id": "counter:8de37b2ca7134b468c105ac9d984281e",
     "video_id": 42,
     "kind": "like",
     "delta": 1
   }
   ```

   `kind` 仅允许 `like`、`favorite`、`comment`，`delta` 仅允许 `+1`、`-1`。消费者用固定映射选择计数字段，禁止将消息字段直接拼进 SQL。用户原先看到 100、点击后显示 101，消息里仍然只传 `+1`，不让客户端提交或覆盖总数。

7. **独立队列与可靠发布。**

   | 项目 | 现有通知链路 | 新计数链路 |
   | --- | --- | --- |
   | Exchange | `feed.events`，topic | 复用 |
   | Routing key | `notification.like.created` 等 | `counter.video.delta` |
   | Queue | `feed.notification` | `feed.counter` |
   | Binding | `notification.#` | `counter.#` |
   | DLQ | `feed.notification.dlq` | `feed.counter.dlq` |
   | DLX | `feed.dlx` | 复用 |
   | 死信 routing key | 保留现有 `dead` | 新增 `counter.dead` |

   计数队列与 DLQ 先声明，再允许发布计数事件。不能把两条 DLQ 都绑定到同一个 direct routing key，否则会收到彼此的死信。

   Publisher 对既有通知事件保留原路由；对 `counter.video.delta` 使用同名路由；未知类型显式报错。保留持久化消息、durable 队列、Publisher Confirm、`mandatory` 与 Return 检查，以及 `claimToken` 条件标记。只有 Broker 确认且没有无法路由退回时，才标记 Outbox 已发布。

   当前认领使用 `FOR UPDATE SKIP LOCKED` 和两分钟租约，可继续复用。Broker 已接收但 Outbox 标记失败时会重复发布，由计数消费者去重。

   连接可以复用，计数消费者必须使用自己的 Channel 和消费参数。调整 MQ 层为明确指定队列的辅助方法，不把通知队列改成计数队列，也不让两种消费者竞争同一个队列。

   现有 Publisher 每 200ms 调用一次、每次最多 100 条，且逐条等 Confirm。增加计数事件后需要测 Outbox 发布能力；设计为满批后继续认领下一批，未满批或为空时再等待，避免固定空转间隔成为积压来源。暂不增加并行确认窗口或另建发布框架。

8. **计数 Worker：有限批次，事务去重，提交后 ACK。**

   第一版初始参数如下，均为待压测的配置值：

   | 参数 | 初值 |
   | --- | --- |
   | 活跃计数 Worker | 部署层面共 1 个；不是每个 HTTP 实例自动开 10 个 |
   | Prefetch | 100 |
   | 批次上限 | 100 条 |
   | 等待成批时长 | 100ms，满批立即处理 |
   | autoAck | false |

   Prefetch 是未确认消息上限，不是每秒处理速率。容量控制来自有限 Worker、有限批次和实际处理能力；需要硬性速率预算时再增加明确限速。多开 Worker 必须仍正确，但不会自动提高同一视频的写入能力。

   ```text
   收集最多 100 条消息，或等到 100ms 到期
   校验消息；格式或版本不合法的消息转入计数 DLQ
   开始一个数据库事务
     按 event_id 稳定顺序逐个插入消费记录
       对应主键重复：跳过该事件
       插入成功：纳入本批增量
       其他错误：回滚整批
     将新事件按 video_id、kind 求和
     按 video_id 升序更新计数行；同一视频三个增量一次更新
   提交事务
   对本批已提交消息逐条 ACK
   ```

   必须先通过数据库去重，再计算本批待应用增量；不能先把重复消息也求和。某种增量相抵为零时仍登记事件，但可跳过对应计数更新。

   例如，一个有效批次里视频 42 有 80 次点赞、10 次取消、5 次收藏，可以对这条计数记录执行一次 `likes_count + 70, favorites_count + 5`。这只是计数更新次数减少；业务事实、Outbox 和去重记录的写入仍然存在，SQL 总量不保证更少。

   数据库提交前崩溃：事务回滚，消息未 ACK，重投后再处理。提交后、ACK 前崩溃：重投时消费记录已存在，不重复计数。内存批次中的消息未提前 ACK，进程退出时可以重新投递。

   暂时性数据库错误回滚且不 ACK，关闭失败 Channel，并采用退避重新消费，避免快速死循环。坏消息进 DLQ 后保留告警和人工修复入口；不能把进入 DLQ 当成计数已经收敛。第一版不自动清理消费去重记录，后续保留期必须覆盖全部重投、DLQ 恢复及允许的历史重放范围。

9. **乱序可以处理，但不能在存储层随意截断。**

   多个 Publisher、重试或重新投递可能使删除事件先到。只要每个有效事件应用一次，正负增量求和与顺序无关。

   若基数为 0，先收到 `-1` 再收到 `+1`，存储依次为 `-1`、`0`，最终正确。若每次扣减都使用 `GREATEST(count - 1, 0)`，就会变成 `0`、`1`，最终多算。

   因此数据库保存有符号中间值，响应展示时才取 `max(0, count)`。队列排空且没有失败事件时，计数必须与事实表一致；持续负值或对账偏差需要排查，不能用展示截断掩盖错误。

10. **前端和接口契约。**

    点赞响应改为 `{"is_liked":true,"changed":true}`，收藏响应为 `{"is_favorited":true,"changed":true}`，可保留原 message 字段。重复操作可以返回 `changed:false`，不承诺同步最新总计数。

    评论发布仍同步返回保存后的 comment；删除返回成功和实际变更结果，不再让页面依赖同步精确的 `comments_count`。列表和详情响应继续提供最终一致的计数字段。

    前端保存点击前状态和数字，立即切换状态并加减一次；请求成功后以服务端互动状态校准，不再根据响应重复加减，也不拿旧全局计数覆盖本地数字。请求期间保留逐视频 busy，避免当前页面并发翻转同一操作。

    确定失败时恢复旧状态；网络超时代表提交结果不确定，应查询状态或幂等重试目标状态后校准。重试使用“设为已点赞/未点赞”，不使用“反转当前状态”。页面重新加载后显示当前服务端快照，允许计数暂时落后。

    `changed:false` 不表示前端必须撤销本地展示。例如另一设备已经点赞，本页面刚从旧状态切成已点赞，可以保留确认后的状态和暂估数字。

11. **读取计数与缓存。**

    元数据继续使用当前视频缓存。第一版计数直接按本页视频 ID 批量查询 `video_counters`，在响应组装时覆盖公共计数；一次列表一个批量查询，禁止逐视频查询。第一版不额外引入 Redis 计数缓存，减少缓存失效与消费提交之间的时序问题。

    需要覆盖最新流、关注流、榜单视频组装、视频详情、作者作品、我的点赞、我的收藏等所有返回计数的路径。旧视频缓存中的计数不能直接用于最终响应；切换时作缓存版本隔离或统一清理，并确保新组装始终使用计数投影。

    请求写互动后不再为了计数清除整条视频资料缓存。计数事件也不必触发资料缓存失效。现有小时桶榜单继续基于事实表填充，不在本轮顺便重写榜单算法。

12. **删除视频与互动并发，不能靠普通存在性查询解决。**

    计划为 `likes.video_id`、`favorites.video_id`、`comments.video_id` 和 `video_counters.video_id` 建立真实的视频外键。迁移前核对存量孤儿、列类型、引擎和索引。继续由删除事务清理子表和计数，再删除视频；使用约束拒绝并发产生孤儿，不仅修改 GORM 注释。

    InnoDB 外键检查可能取得父行共享锁；多个互动的共享锁可以并存，但删除、修改视频的排他锁仍可能与它们冲突。这是生命周期保护，不是原来三类互动主动拿同一个父行排他锁。`view_repo.go` 的现有视频行更新也会与这种共享锁产生冲突，混合负载必须测出这一剩余影响，后续可将播放计数接入同一异步链路。

    消费端只 UPDATE 已存在的计数行，不为每个事件 UPSERT 创建视频计数，防止迟到事件把已删除视频的计数重新建出来。遇到不存在的计数行，要核实视频确实已删除再记录已消费并跳过；视频仍存在则视为投影缺失故障，修复后重试，不能静默丢掉事件。

    删除视频会删除当前事实及计数，不必给每条子记录额外发送扣减事件。尚未到达的计数事件按上面的删除检查终止；历史通知仍按当前语义保留。

13. **切换与回退。**

    本学习项目采用短暂停写切换，避免先引入双写、CDC 或多版本回放机制：

    - 停止所有修改这些互动事实的写入口，确保旧版本写入进程退出；核对/修复孤儿记录后执行表和外键迁移。
    - 从 `likes`、`favorites`、`comments` 按视频聚合回填，未有互动的视频填零。不能只相信可能已经漂移的旧冗余计数。
    - 启动新拓扑、Publisher 和计数消费者，部署已完成修改的后端和前端，清理旧缓存；确认全部写路径已切换，再开放写入。
    - 不把历史通知 Outbox 当成历史计数事件重放，否则会与回填重复计数。计数事件从切换后的真实变更开始生成。

    需要回退时再次停写，处理完或明确隔离待应用计数事件，按事实表重算旧 `videos` 计数，停止新计数写入后再恢复旧版本及前端。不能直接回退代码并让旧同步写与新消费者同时更新计数。

14. **验收关注接口和后台两部分。**

    功能及故障检查包括：重复点赞/取消、并发同用户操作、不同用户同时操作、自己的视频计数、重复投递、正负事件乱序、消费提交前后故障、Broker 运行期断开恢复、Outbox 租约重认领、视频删除并发、迟到事件、投影缺失、坏消息、前端成功/失败/超时校准及所有列表读取路径。

    Broker 运行期暂不可用时，已运行的接口可以先提交 Outbox；当前 main 启动仍要求 RabbitMQ 成功连接，不能据此宣称 Broker 故障时新 API 进程也一定能启动。

    负载用相同硬件、连接池、数据规模、登录态、请求分布和预热条件，分别对比原实现与完整候选实现；隔离测试数据库，保存基线提交与原始结果。

    | 负载 | 检验目标 |
    | --- | --- |
    | 单视频、不同用户新增点赞 | 原始视频排他锁串行瓶颈 |
    | 单视频混合点赞/收藏/评论 | 不同互动互相竞争的改善 |
    | 多视频分散互动 | 异步消息和去重带来的额外成本 |
    | 突发后降至低流量 | 削峰后的积压及追赶时间 |
    | 暂停计数消费者后恢复 | 接口反馈与计数处理解耦及恢复正确性 |
    | 加入播放上报及视频删除 | 剩余父行冲突和生命周期约束 |

    新增点赞负载需使用未点赞的用户/视频组合；取消需预建关系；连续测试可让每个用户串行交替状态。记录真实变更比例，避免大量重复点赞返回 200、实际不写业务事件，却被当作新增点赞吞吐。

    接口记录成功 QPS、业务变更数、错误率、p50/p95/p99、事务时间和锁等待；后台记录 Outbox 未发布数与最老年龄、发布速率、队列 ready/unacked、消费速率、事件提交到投影更新的延迟、DLQ 及批量合并率。不能只记录 RabbitMQ 队列长度，因为消息可能先积压在 Outbox。

    队列排空、发布完成、没有待修复死信并停止写入后，逐视频比较计数与事实表 COUNT；必须完全一致。正常无积压时先以投影 p95 延迟不超过 1 秒为测试目标，实际结果由测试确认。

    若峰值输入为每秒 10000 个计数事件、消费能力为每秒 2000 个，峰值期间积压每秒增加约 8000 个。输入回落且低于消费能力后才能排空。这是说明机制的假设数据，不是本项目实测。

16. **实现与验证记录（2026-11-15）。**

    已接入三类互动的增减事件、独立计数表、消费去重、批量消费、提交后 ACK、独立计数队列与 DLQ、前端本地加减及查询确认。使用 RabbitMQ `x-single-active-consumer`，多 API 实例也只有一个活跃计数消费者，其余实例可以接替。消费注册与退出由同一个 Run 管理，避免取消消费 RPC 与关闭 Channel RPC 并发竞争。

    迁移命令为 `backend/cmd/migrate-counters`。先停写、确认没有未处理计数事件，再运行 `go run ./cmd/migrate-counters -offline`，按事实表回填后启动。已删除视频的晚到事件只保留消费记录、不创建计数；现存视频缺少投影会报错。读取时若视频在元数据读取后被删除，允许这次旧快照结束，不误报存量迁移缺失。

    本次验证包含关系与计数解耦、重复和乱序消息、消费事务回滚、数据库提交后 ACK 失败再投递、真实队列的暂停消费及恢复、坏消息进入独立 DLQ、删除并发及外键拒绝孤儿、旧缓存计数被投影覆盖、离线回填和启动保护。测试使用专用数据库和 Exchange/队列，没有切换开发库或提交/推送代码。

17. **本机热点接口性能对比（2026-11-17）。**

    基线为改动前提交 `30d3a6b`，候选为当前异步计数工作区。Mac arm64、Go 1.24.5；同一台本机 MySQL 26.7，分别使用全新隔离数据库；同一 Redis 进程的独立 DB；同一 RabbitMQ 4.1 的独立 Exchange 和队列。候选和基线都通过真实 Gin API、JWT 中间件及 Redis 会话缓存运行。

    每轮 128 并发、5000 个已认证请求，每个请求由不同账号对同一个视频产生真实状态变更；点赞负载为 5000 次点赞，混合负载为 1667 次点赞、1667 次收藏和 1666 条评论。每种负载各跑三轮，基线/候选交替顺序。全部请求返回成功（评论使用正常的 HTTP 201），无重复点赞空操作。QPS 是成功响应数除以该轮客户端总耗时；延迟是客户端逐请求计时的 p50/p95/p99。

    | 热点负载 | 版本 | 三轮 QPS | 中位 QPS | 中位 p50 | 中位 p95 | 中位 p99 | 中位排空时间 |
    | --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
    | 点赞 | 同步基线 | 334 / 391 / 401 | 391 | 297.9 ms | 505.9 ms | 737.1 ms | 12.1 s |
    | 点赞 | 异步计数 | 1167 / 1128 / 1281 | 1166 | 82.5 ms | 229.7 ms | 273.7 ms | 30.6 s |
    | 点赞/收藏/评论混合 | 同步基线 | 405 / 494 / 398 | 405 | 269.3 ms | 439.8 ms | 492.9 ms | 12.6 s |
    | 点赞/收藏/评论混合 | 异步计数 | 1155 / 1124 / 1384 | 1155 | 78.9 ms | 224.5 ms | 269.5 ms | 35.7 s |

    在这个本机热点负载下，点赞接口中位吞吐提高约 2.99 倍，混合负载提高约 2.85 倍；两种负载的 p95 分别下降约 54.6% 和 49.0%。所有最终计数均与预期一致，Outbox 未发布数及相关队列 ready/unacked 最终均归零。

    “排空时间”从最后一个 HTTP 响应后计时，直到计数达到预期、Outbox 没有待发布行、通知队列及计数队列都没有 ready/unacked 消息。候选每次外部互动通常写两条 Outbox 事件（计数和通知），同步基线只有通知事件，所以这个指标包含不同数量的后台工作，不是同工作量的纯消费者速度对比。实测也显示当前逐条等待 Publisher Confirm 的发布器会形成明显追赶时间；高接口 QPS 不能直接当作后台长期稳态消费能力。

    这是同一台开发机、本地 MySQL、单视频热点、固定 128 并发的 API 端到端实验，不是生产容量承诺；尚未测试长时间稳态输入、更多视频分片、远程数据库或多 API 实例扩展。原始逐轮数据保存在本机 `/tmp/feedbench_20261117_c9c747dd_results_v4.json`。
